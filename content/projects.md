# A06｜從會看程式到能獨立設計系統

原則：不以天數強迫進度，而以「概念、修改、除錯、測試」四種能力決定是否升級。

## 第一階段：入門工具（第1–3章）

作品：互動式猜數字遊戲。需求：輸入錯誤可重試、值域檢查、統計猜測次數、離開時顯示結果。不可直接 copy 外部完整答案。

驗收：cargo fmt / check / test；能解釋每個語法元素和程式對輸入的反應。

## 第二階段：資料模型（第4–9章）

作品：RPG 背包與任務狀態管理器。需求：以 struct 保存角色、以 enum 保存任務狀態、Vec 保存物品、HashMap 保存資源數量、Result 處理輸入錯誤。

測試：空背包、重複物品、負面或非法輸入、超過上限；驗證狀態不可互相矛盾。

核心問題：誰擁有物品？何時只需要 &T？何時需要 &mut T？

## 第三階段：可維護 CLI（第10–14章）

作品：搜尋文字與整理紀錄工具。需求：分離 lib.rs / main.rs、泛型或 Trait 適度抽象、讀寫檔案、以 Result 傳播錯誤、用 Cargo 測試。

驗收：核心邏輯在沒有實際檔案時也能測試，CLI 遇到不存在檔案要給清楚錯誤，輸出與錯誤輸出要分開。

## 第四階段：共享狀態與並行（第15–17章）

作品：多工作者處理待辦任務佇列。需求：先用 channel 傳遞任務、使用 Arc/Mutex 共享必要統計、使用受限 worker 數量、對失敗有明確處理。

驗收：無資料競爭、能優雅停機、能在測試中重現取消與關閉時的狀態；說明為何選用 threads 而不是 async 或反過來。

## 第五階段：類型設計與系統邊界（第18–21章）

作品：本地 HTTP 服務原型。需求：解析最小請求、產生正確回應、有限資源的 worker queue、正確的 Content-Length、可測試的路由邏輯。

驗收：錯誤輸入不直接崩潰；提供 timeout；能指出原型不適合對外網開放的缺陷，並比較成熟 HTTP framework 的能力。

## 第六階段：依興趣分流

路線 A：手機 Termux CLI 自動化。作品：可在原生 Android Termux 運行的檔案整理器，使用最少依賴、記錄耗電和儲存成本。

路線 B：ESP32 感測器警報。作品：UART 或 I2C 資料解析、狀態判定、LED/蜂鳴器控制；需根據實際晶片與 HAL 配置工具鏈。

路線 C：瀏覽器 Wasm 計算核心。作品：把純 Rust 算法導出給 JavaScript，測試桌面與 Android 瀏覽器。

路線 D：遊戲計算核心。作品：固定更新率模擬角色移動/狀態/簡單碰撞，與 GPU 渲染解耦，測試決定性。

## 怎麼做專案複盤？

每個專案至少交付：README（為何做、如何執行）、需求、架構圖、主要資料型別、錯誤案例、測試案例、建構指令、已知限制。

重構時先指出重複、耦合、無法測試的根因，不把「檔案拆更多」或「使用更複雜 trait」當成改善本身。

## 能力驗收量表

初階：看懂語法並能修改示例。中階：能從需求選型別與所有權方向。高階：能設計模組、錯誤與測試。進階：能分析並行、非同步、效能與安全邊界。

所有階段都需要：解釋為什麼，預測修改後會發生什麼，遇到失敗能指出是哪個假設被違反。

## 自我測試的五個問題

1. 我現在解決的是什麼問題？

2. 目前設計的不可變條件是什麼？

3. 資料的所有權在哪裡？哪個地方只是借用？

4. 失敗會如何傳播與被處理？

5. 如何用一個測試證明修改沒有破壞原本行為？

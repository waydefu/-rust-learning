# 第04章｜所有權、借用與切片：Rust 的核心

假設你有一本漫畫，想給朋友看。你可以把書送給他、借給他，或買一本新的給他。這三種做法看似差不多，但誰可以使用這本書、誰負責保管它，答案都不一樣。

電腦也有類似的問題：兩段程式都想使用同一份資料，究竟誰負責保管？什麼時候可以修改？用完後又由誰清理？Rust 把這些問題變成一套能在編譯時檢查的規則，稱為所有權（ownership）。

**先備知識：** 只要認得 `let`（替值取名字）、`mut`（允許修改）、`fn`（定義函式）與 `println!`（顯示文字）就能開始。忘記了可以回到[第 3 章](../fundamentals/)。本章會第一次介紹的符號，都會在使用時解釋。

閱讀時先不要背規則。每遇到一段程式，問自己三件事：

- 現在誰負責保管資料？
- 誰正在使用資料？是只讀，還是要修改？
- 資料何時可以被清理？

這三個問題將貫穿整章。先建立直覺，再學正式術語；最後要能自己推導答案，而不是只記住哪些程式會報錯。

> **名字還在，資料就一定還在嗎？** <!-- callout:context -->
>
> 書送出去以後，你仍然記得它的名字，但已經不再擁有它。程式中的變數也是如此：名稱能不能繼續使用，取決於它是否仍持有有效的值。要理解這條規則為什麼重要，我們得先看看電腦如何保管資料，以及資料用完後會發生什麼事。

## 一、問題從哪裡來：記憶體生命週期

### 先認識記憶體：電腦的工作桌

想像你正在玩遊戲。角色的血量、名字、背包物品，都需要有地方暫時保存。程式執行時使用的記憶體（memory），可以先想成一張有許多格子的工作桌。它與儲存照片、存檔的磁碟不同，這裡討論的是程式運作期間使用的空間。

每格可用來保存資料，而資料會由位元組（byte）組成。一個位元組有 8 個位元（bit），每個位元可以是 0 或 1。例如 `i32` 是一種固定使用 32 個位元的整數型別，所以它的值大小固定為 4 個位元組。

可是角色的名字可能只有 2 個英文字母，也可能有 20 個；玩家還可以一直增加文字。電腦必須在需要時取得足夠的空間，並且記得這些空間的位置。

### 固定大小和可成長資料為何不同？

- 堆疊（stack）：可先想成依照函式呼叫安排的工作區，通常適合存放編譯時已知大小的區域資料。
- 堆積（heap）：可先想成依需求借用的空間。程式執行時可以要求一塊空間，在不再需要時歸還。
- 指標（pointer）：像一張寫著位置的紙條，記住資料在哪裡，而不是把整份資料都寫在紙條上。

Rust 的 `String` 是可以成長的文字型別。對非空的普通 String，它通常有一個在堆積配置的文字緩衝區，並記錄三種資訊：指標（文字在哪裡）、長度（目前使用幾個位元組）、容量（最多可在現有配置中容納幾個位元組）。例如內容是 Rust 時，長度為 4，容量至少為 4。

這些名詞只用來建立概念，不代表編譯後每個區域值必然存在堆疊，也不是說所有 String 都一定取得堆積空間，例如空 String 可以不配置。實際位置可能受編譯器最佳化影響。

堆積配置需要分配、回收；若忘記回收就是洩漏，太早回收就可能留下懸空指標，同一份配置回收兩次更可能造成記憶體破壞。

### 為什麼一定要決定何時歸還？

假設程式向記憶體借了 100 格來保存文字，使用完畢卻沒有歸還。下一次又借 100 格。長期累積，就可能把可用空間耗光。這叫記憶體洩漏（memory leak）。

反過來，還在使用的格子如果太早歸還，其他資料可能占用原本的位置；舊指標若仍被拿來讀寫，就像拿著已經失效的門牌去找東西。把同一塊空間歸還兩次，也會破壞記憶體管理的正確性。

不同語言有不同處理方式。某些語言讓程式設計者明確分配及釋放記憶體；另一些使用垃圾回收（garbage collection，GC），例如由執行時系統追蹤哪些物件已不可達並回收。Rust 選擇另一條路：讓編譯器先檢查資料的所有權和借用關係，正常情況下在值被銷毀時自動清理資源，不需要常駐的追蹤式 GC。

這不是說 Rust 保證永不洩漏：刻意忘記值或形成某些循環共享所有權仍可能洩漏。Rust 主要保證安全程式碼不會因違反這些規則而產生未定義行為。

比喻：堆積是圖書館倉庫；持有所有權者是唯一負責歸還該書的人；借用者有閱覽權，但不自動取得「歸還責任」。要注意這是責任分配模型，不代表任何時刻只有一個人能讀，也不是所有類型都真的放在堆積。

## 二、三條基本規則，因果連續

### 先用送書建立直覺

一本書由小明保管。他把書送給小華之後，就不能再假裝自己還保管那本書。Rust 中的所有者（owner）是負責某個值生命週期的所有權位置；對直接持有的 String，可以先把綁定名稱想成負責保管它的人。

作用域（scope）則是名稱有效的程式範圍，通常由一對大括號界定。在正常離開作用域時，仍由區域變數持有的值會依 Rust 的規則被銷毀。對 String 而言，這通常包括歸還它管理的堆積空間。

先從最簡單的直接所有權開始，規則就容易理解了：

1. 先以一個直接持有的 `String` 為例，每份配置有一個負責清理的所有權位置。共享所有權是 [第 15 章](../smart-pointers/) 的另一種模型。

2. 所有者離開有效作用域時，值通常會被清理（Drop 可以自訂清理行為）。

3. 將非 Copy 值以值傳遞給新所有者時，原本的綁定不再能使用它，避免兩個擁有者在作用域結束時重複釋放。

```rust run
fn main() {
    let a = String::from("hello");
    let b = a;                     // 移動所有權
    println!("{b}");
    // println!("{a}");            // 若取消註解，會觸發 E0382
}
```

逐行讀這個範例：

- `String::from("hello")`：建立擁有文字 hello 的 String。雙冒號表示從 String 型別中呼叫名為 from 的關聯函式。
- `let a = ...;`：建立名稱 a，讓它持有這個值。
- `let b = a;`：把值移到 b。這稱為移動（move）；不是另外買一本書，也不是把文字內容複製成兩份。
- `println!("{b}");`：把 b 的內容顯示出來，得到 hello。花括號內的 b 是格式字串要代入的變數。
- 以 `//` 開頭的是註解，不會執行。若取消最後一行的註解，就會試圖使用已經移動的 a。

請先用手指沿著互動記憶體圖的箭頭追蹤 a 和 b：所有者從 a 變成 b，文字緩衝區並沒有因此被複製。

為何 String 賦值不自動複製文字？深層複製會配置新記憶體，成本不小。Rust 選擇預設移動（move），需要複製時再明確請求 `clone()`。對這個非空的 `String`，複製後兩個值分別管理各自的緩衝區。

```rust run
let a = String::from("hello");
let b = a.clone(); // 新配置、複製資料，a 與 b 各自擁有
```

### 用作用域看看誰負責清理

```rust run
fn main() {
    let a = String::from("Rust");
    {
        let b = a;
        println!("{b}");
    }
    println!("內層區塊已結束");
}
```

這次有兩組大括號。b 在內層區塊建立，取得原本由 a 持有的 String；內層區塊結束，b 被銷毀，String 的緩衝區被釋放。外層程式仍然可以繼續印出「內層區塊已結束」，但不能再使用已經移動的 a。

這正是所有權想解決的問題：不需要手動數誰該釋放同一塊空間，Rust 會依照所有權的位置決定責任。

### 從 E0382 找出移動位置

```rust error E0382
fn main() {
    let a = String::from("hello");
    let b = a;
    println!("{a} {b}");
}
```

診斷會指出 `a` 的原始綁定、所有權移到 `b` 的位置，以及最後借用 `a` 的位置。先判斷需求。若只想觀察同一份字串，可用 `let b = &a;`。若兩邊都要獨立修改，再用 `let b = a.clone();`。若修改責任已交給 `b`，後續統一使用 `b`。

> **交出、複製，還是暫時借用？** <!-- callout:analogy -->
>
> 對 `String` 而言，move 像交出原本的書，`clone()` 像買另一份，`&` 像取得閱讀權，`&mut` 像暫時取得獨占修改權。這些是語意比喻，不表示實際執行時必然搬移記憶體，也不代表借用是在執行時上鎖。

> **跟著 a 和 b 追蹤同一份字串** <!-- callout:walkthrough -->
>
> 第一段 hello 範例：a 建立並持有 String；`let b = a;` 讓 b 接手；`println!` 讀 b。若改讀 a，編譯器會拒絕。可以配合頁面的記憶體圖，追蹤相同緩衝區由誰負責清理。

## 三、那 i32 為什麼可以重用？

```rust run
let x = 5;
let y = x;
println!("{x} {y}");
```

預期輸出是 5 5。與前一個 String 範例不同，小小的整數可以直接複製成另一份獨立的值。

這可以編譯，因為 i32 實作 Copy：賦值產生獨立的位元複本，沒有需要保護的獨占堆積配置。Copy 不是按名稱區分「基本型別」或「複雜型別」；依型別是否實作該 trait 而定，實作 Drop 的型別不能是 Copy。

## 四、為何要「借用」？

如果你只想知道朋友那本漫畫有幾頁，需要請朋友把書送給你嗎？當然不需要。他只要暫時借給你看，就能保留原本的書。

同樣地，若函式只想計算字串長度，沒有理由拿走整個 String。Rust 提供參考（reference）來表達暫時存取的關係；建立參考並使用它的過程稱為借用（borrow）。

在程式碼中，型別前面的 `&` 表示共享參考，例如 `&String`。這與直接持有 String 不同：你可以透過參考讀取資料，卻不會因此取得那份 String 的所有權。

```rust run
fn size(s: &String) -> usize { s.len() }
fn main() {
    let name = String::from("Rust");
    let n = size(&name);
    println!("{name} {n}");
}
```

把範例拆開來看：`fn size(s: &String) -> usize` 宣告了一個函式，參數 s 是 String 的參考，箭頭後的 usize 是回傳值的型別，常用於長度或索引。`s.len()` 是呼叫 len 方法，取得文字的位元組數。Rust 這四個英文字母各占一個 UTF-8 位元組，所以結果是 4。

`size(&name)` 的 &name 建立共享參考，讓函式暫時存取 name；在這個 String 範例中，參數 s 只能透過此參考閱讀，不能直接修改 String。讀完後原所有者 name 仍有效。Rust 常偏好借用 &str 而不是 &String，因為更通用。

## 五、共享閱讀與獨占寫入：為何這樣限制？

假設兩個同學正在看公告欄的文字，這沒有衝突。但如果第三個同學突然把公告撕下並換成新的一張，原本正在閱讀的人就可能拿著過時的位置。Rust 對這類可能重疊的存取有一個原則：共享閱讀可以同時存在；需要獨占修改時，就不能有其他衝突的存取。

在語法上，`let mut name` 允許修改 name 持有的值；`&mut name` 建立可變參考，讓持有參考的一方獲得受約束的獨占存取權。兩個 mut 看似相同，位置和責任卻不同。先看實際例子。

```rust run
let mut name = String::from("R");
let r = &name;       // 共享借用
println!("{r}");     // 最後一次使用 r
let w = &mut name;   // 可變借用，與 r 的有效使用期不重疊
w.push('!');
println!("{name}");
```

依順序追蹤：第一行建立可修改的字串 R；第二行 r 借來讀；第三行印出 R，是 r 的最後一次使用；第四行 w 借來修改；第五行 push 將字元 ! 加到字串尾端；最後印出 R!。這裡沒有兩次衝突的借用同時有效。

同一期間可以存在多個共享借用 &T；或者一個獨占的可變借用 &mut T，不能同時有重疊的互斥存取。目的不是限制自由，而是防止「有人正在讀時，別人把資料改動或移走」。

比喻：多個人可同時查看公告欄；要更換內容時，需要在修改期間排除其他讀寫者。比喻的邊界：真實借用不是執行時上鎖，通常在編譯時分析；使用生命週期、別名分析與型別規則確保存取安全。

## 六、借用何時結束？不是機械地等到大括號

先分清兩件事：變數名稱仍然在作用域內，不代表透過該名稱進行的借用必須一直維持。就像你在下課前歸還一本書，下一位同學不必等到整節課結束才能借。

Rust 使用非詞法生命週期（non-lexical lifetimes，NLL）等分析，借用有效期常到它的最後一次使用，而不一定要持續到變數宣告所在區塊結尾。編譯器依實際使用與控制流程判斷。

```rust run
let mut s = String::from("ok");
let view = &s;
println!("{view}");
s.push('!'); // 此時 view 不再被使用
```

這段程式印出 ok，然後才把 ! 加上去。即使 view 的名稱到區塊結束前仍在作用域內，編譯器也看得出後面沒有使用 view，因此這次修改合法。

最重要的是「有沒有重疊存取」，不是「名字還在不在」。如果把最後一次讀取移到修改後面，情況就改變了。

### 為什麼後移最後一次讀取會觸發 E0502？

```rust error E0502
fn main() {
    let mut s = String::from("Rust");
    let view = &s;
    s.push('!');
    println!("{view}");
}
```

`push` 要借用 `&mut String`，容量不足時可能更換緩衝區。由於 `view` 稍後還要讀取，兩個借用會重疊。把輸出移到 `push` 之前可先結束讀取。若想印更新後的文字，先呼叫 `push`，再建立新的共享借用。

> **借用結束看的是最後一次使用** <!-- callout:warning -->
>
> 共享參考的名稱尚在作用域，不代表借用一定延續到大括號結尾。追蹤最後一次使用，再看是否與修改重疊。遇到 E0382 或 E0502，先找責任與存取衝突，不要一律用 clone 消除錯誤。

## 七、懸空參考到底危險在哪？

想像你把遊樂場置物櫃的號碼告訴朋友，但在朋友抵達之前，你已經把置物櫃退還給管理員。即使號碼還在紙上，也不能保證櫃子裡仍是你的物品。程式中的懸空參考（dangling reference）就是指向已不再有效的資料的參考。

生命週期（lifetime）是 Rust 用來描述參考必須有效多久的關係，不是計時器，也不會讓值活得更久。以下範例試圖將函式內建立的資料的參考交給外面，看看編譯器為什麼拒絕。

```rust error E0106,E0515
fn broken() -> &String {
    let s = String::from("gone");
    &s
}
```

這段反例先觸發 E0106，因為函式沒有可供推導輸出生命週期的參考參數。就算寫上 `fn broken<'a>() -> &'a String`，仍會觸發 E0515。
原因是 `s` 在函式結束時清理，無法把指向區域資料的參考交給呼叫者。

正確做法 A：回傳擁有的 String。

```rust fragment
fn make_name() -> String {
    String::from("safe")
}
```

正確做法 B：若資料由呼叫者持有，可以回傳借用，並由生命週期約束來源。此例的參考輸入只有一個，Rust 能省略生命週期標註。比較兩個借用輸入的寫法見 [第 10 章](../generics-traits-lifetimes/)。

```rust run
fn first_line(s: &str) -> &str {
    s.lines().next().unwrap_or("")
}
fn main() {
    let text = String::from("第一行\n第二行");
    assert_eq!(first_line(&text), "第一行");
}
```

## 八、String 與 &str 到底差什麼？

先回想「整本書」和「借來閱讀的一段文字」。如果函式只想看文字，接受一段借來的文字通常比要求某種特定的擁有者更有彈性。

UTF-8 是把 Unicode 字元表示為位元組的一種編碼方式。英文字母 R 通常使用 1 個位元組，中文字「中」使用 3 個位元組，所以文字的位元組數不一定等於看到的字數。

String 是擁有 UTF-8 位元組緩衝區的可成長字串；&str 是指向有效 UTF-8 資料區段的借用切片（指標 + 長度的概念），不一定由自己擁有資料。字面量 "hello" 的型別通常是 &'static str，資料存在程式可使用的靜態儲存區。

```rust fragment
fn greet(name: &str) { println!("你好，{name}"); }
let owned = String::from("Rust");
greet(&owned);
greet("世界");
```

用 &str 當閱讀參數通常能同時接收 String 借用與字串字面量。

## 九、切片解決什麼問題？

切片（slice）像把尺放在一整排資料上，指定「我只要看從哪裡開始到哪裡結束」，不必複製整排內容。Rust 使用參考來保留這種區段和原始資料的關係。

例如 `&s[0..2]` 表示借用 s 的第 0 個位元組到第 2 個位元組之前的範圍，不包含位置 2。對 String 或 str，這些位置必須落在合法的 UTF-8 字元邊界。

假設函式回傳字串中第一個單字的整數索引。若原字串被修改，舊索引可能不再對應正確資料。&str 切片把「哪一段資料」與借用關係綁在一起，讓編譯器追蹤有效性。

```rust run
fn first_word(s: &str) -> &str {
    s.split_whitespace().next().unwrap_or("")
}
```

這是按 Unicode 空白分隔的示範；切片以位元組為索引，不能隨意在 UTF-8 字元中間切開，例如 &s[0..1] 對中文字可能在執行時 panic。需要依字元或使用者感知字素處理時應另選 API。

## 十、記憶體圖：把 move 與 borrow 連起來

String 的「指標/長度/容量」是管理資料的值。move 使原綁定失效，把管理責任轉交；clone 建立另一份內容；& 只是受約束地查看；&mut 是受約束地修改。

不要誤以為 move 一定會產生機器層級的位址搬遷：所有權語義與最終機器碼的實際複製、最佳化不是同一件事。也不要認定所有局部值必定位於堆疊：編譯器可最佳化。

## 十一、編譯器診斷讀法

遇到 use of moved value，找出哪個位置消耗了所有權；遇到 cannot borrow as mutable，檢查 mut 與活躍借用；遇到 does not live long enough，追資料主人何時被釋放；不要只用 clone() 掩蓋設計問題。

## 十二、動手驗收與答案

### 先猜結果，再打開終端機

把下面的程式放進自己的 `main.rs`，先用紙筆畫出哪個名稱擁有 String、哪個名稱只是借用，再執行。

```rust run
fn main() {
    let mut a = String::from("Rust");
    let b = &a;
    assert_eq!(b.as_str(), "Rust");
    a.push('!');
    assert_eq!(a.as_str(), "Rust!");
}
```

`assert_eq!` 是檢查兩邊是否相等的巨集：不相等就會讓程式 panic（中止正常流程）；相等時不印出任何文字。這裡兩次檢查都會成功。b 最後一次使用是第一個檢查，接著才能透過 a 修改原值。as_str() 取得 String 內容的共享字串切片。

現在把第一個檢查移到 push 之後，先預測結果，再試著用編譯器確認。若出現 E0502，回到第五、六節，找出哪兩種借用重疊；不要先用 clone 繞過問題。

### 用自己的話回答

題1：把 String 傳給 fn consume(s: String) 後為何不能再用？因所有權移入函式，呼叫者的綁定無效。

題2：只需閱讀時改成 fn consume(s: &str)，呼叫時 &name；解釋為何較通用。

題3：為何同一段期間不允許一個 &mut 與任何可能存取相同資料的 &？因讀寫衝突可能破壞參考有效性與資料不變條件。

題4：使用 String::clone 後，修改 b 是否會修改 a？不會，兩份擁有獨立緩衝區。

題5：拆解 let first = &s[0..2]，確認範圍是 byte offset，對中文字測試前先閱讀 UTF-8 章節。

終極驗收：能不背口訣，直接從「誰負責釋放、有哪些活躍借用」推導每個借用錯誤。

### 實作挑戰：借用單字之後再清空字串

用上面的 `first_word` 取得「Rust 課程」的第一個單字。在 `println!` 之前呼叫 `clear()`，預測編譯器會拒絕哪一行。再做兩次修改，分別保留原本的切片與取得一份可獨立存活的字串。

**解析。** 第一版把 `println!` 移到 `clear()` 之前，可以在輸出時維持借用，等最後一次使用後再清空。第二版呼叫 `first_word(&title).to_owned()` 建立獨立的 `String`。此時可以先清空 `title` 再印出第一個單字。多出的一次配置與複製換取了獨立的生命週期。

### 最後帶走的觀念

- 要把資料交給另一個名稱或函式負責：移動（move）。
- 要有獨立的一份資料：依型別使用 Copy 或明確呼叫 clone。
- 只想暫時閱讀：共享借用（&）。
- 需要暫時獨占修改：可變借用（&mut）。
- 想借用連續資料的其中一段：切片（slice）。
- 要確保參考不會比資料活得更久：生命週期（lifetime），第 10 章會深入介紹。

如果你能說明「誰擁有、誰借用、哪裡是最後一次使用」以及為什麼 Rust 需要這些限制，就已經建立了本章最重要的心智模型。還不能解釋時，重做其中一個範例即可，不必重讀整章。
